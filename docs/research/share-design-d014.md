## 1. 資料模型：記錄（record）

每一份資料都是一筆「記錄」，主鍵是 **(原作者 a, 群組 g)**：

| 群組 g | 內容 | 值的格式（傳輸用） | 什麼時候由原作者更新 |
|---|---|---|---|
| `B` | 等級、職業 | `<level>.<classToken>` | 登入、升級 |
| `P` | 全部專業的技能點（含烹飪、釣魚、急救） | `<skillLineID>,<rank>,<max>/…`，照原作者 `GetProfessions` 的順序 | 登入、`SKILL_LINES_CHANGED` |
| `Z` | 所在地 | `<zone>/<subZone>`（`%XX` 轉碼） | 登入、`ZONE_CHANGED_NEW_AREA`（同一個人 5 分鐘最多一次）；取得到所在地時一律分享（D-015） |
| `R<skillLineID>` | 某個專業的配方 ID | 排序後的差值、36 進位，`.` 分隔（同 v1 設計） | 開自己的專業視窗、清單有變 |

每筆記錄帶：

- `t`：原作者**觀察到這個值**的 `GetServerTime()`（記錄時間）
- `h`：值的 24 位元雜湊（36 進位），誰算都一樣
- `v`：值本身

專業名稱不傳：收到的人用自己的客戶端把 skillLineID 換成名稱（`Data.skillName`），配方名稱用 `C_Spell.GetSpellName`。

### 1a. 「確認」和「變更」分開

- 原作者每次觀察（例如登入時讀等級），`t` 就更新成現在。
- 值沒變時，`h` 也沒變。收到「同一個 `h`、比較新的 `t`」的人，**只把 `t` 往後推，不需要傳資料**。
- 所以登入時大家只要交換很小的索引，就知道「這個人的等級在 3 分鐘前還是 60」。只有值真的改了才傳資料。
- 這也讓網站可以依各欄位的時間採用最新值（D-008）。

### 1b. 墓碑（撤回）

一筆 `h = "x"`、沒有值的記錄。和一般記錄一樣比新舊、一樣轉傳。D-015 起 `g` 只有：

- `R<id>`：某個專業的配方。原作者**放棄那個專業**時送出
- 隱私用的 `*`（關閉同步）和 `Z`（關掉分享所在地）已經拿掉：不送；0.9.0 送來的這兩種，收到時忽略
- `P` 不需要墓碑：放棄專業後，新的 `P` 值裡自然就沒有那個專業

收到墓碑：同一個原作者、符合的群組裡，`t` 比墓碑舊的記錄全部刪掉；之後比墓碑舊的資料一律不收。墓碑保留 60 天。

## 2. 訊息格式（prefix `GFTKS`）

- 新 prefix `GFTKS`，取代 v1 設計裡的 `GFTKR`。現有的 `GFTK`（D-011）**繼續收**，收到時轉成 `B`、`P`、`Z` 記錄（見 2c）；0.9.x 也繼續送 `GFTK`，讓還沒更新的 0.8.x 看得到。
- 只走 GUILD 頻道，ASCII，數字用 36 進位，每則最多 250 bytes。開頭是 `S1~<類型>~…`，版本或類型不認得就整則忽略。
- 原作者 `a`：GUID 去掉 `Player-` 前綴（約 13 字）。
- 收到的訊息：sender 必須在自己看到的公會名冊裡；`a` 也必須在名冊裡（用 GUID 比對），不然整則丟掉。

| 類型 | 用途 | 格式 |
|---|---|---|
| `I` 索引 | 某一位原作者的所有記錄（含墓碑）：「我知道 a 的這些」 | `S1~I~<a>~<n>~<g>.<t>.<h>~…`。`n` 是總筆數；放不下時分成幾則，收到的人收齊 `n` 筆才判斷「對方缺哪些」（一位原作者約 5～8 筆，通常 1 則） |
| `Q` 盤點請求 | 「大家手上有哪些人的資料？」 | `S1~Q~<qid>~<作者數>~<總摘要>` |
| `C` 目錄 | 回答 Q：每位原作者一筆摘要 | `S1~C~<qid>~<段>~<共幾段>~<a>.<d>.<m>~…`。`d` 是那位作者所有記錄 `g.t.h` 的雜湊，`m` 是最大的 `t`。每筆約 27 bytes；115 人約 3.1 KB，**約 14 則** |
| `A` 要索引 | 「請給我這幾位的 I」 | `S1~A~<a>~<a>…`（一則最多 15 位） |
| `G` 要資料 | 「請給我這幾筆的值」 | `S1~G~<a>.<g>.<t>~…`（一則最多 8 筆） |
| `V` 小值 | 一則就放得下的值（`B`、`P`、`Z` 幾乎都是） | `S1~V~<a>~<g>~<t>~<h>~<值>` |
| `B` + `D` | 放不下的值（配方） | `S1~B~<a>~<g>~<t>~<h>~<段數>`，`S1~D~<a>~<g>~<t>~<段>~<內容>` |
| `X` 墓碑 | 撤回 | `S1~X~<a>~<g>~<t>` |

### 2a. 收到值（V 或 B+D）

1. 分段 60 秒內要收齊；收齊後重算雜湊，要等於 `h`，否則整份丟掉。
2. 照第 3 節比新舊；收了就更新儲存，畫面跟著更新。
3. **在線的每一個人都可以收**，不只是送 `G` 的那個人。

### 2b. 分享所在地的限制

- 原作者關掉「分享所在地」：送 `X~a~Z`，之後不再產生 `Z`。
- 轉傳的人：只要手上有比 `Z` 記錄還新的 `Z` 墓碑，就不送那份 `Z`。收到墓碑時也已經刪掉了，所以實際上「手上沒有」。
- 原作者重新打開分享：新的 `Z` 時間比墓碑新，自然恢復。

### 2c. 相容 `GFTK`（0.8.x）

- 收到 `GFTK` v1：sender 就是原作者，`a` 取名冊裡 sender 的 GUID。
  - `T`（capturedAt）是對方電腦的 `time()`，當成 `t` 用。電腦時鐘通常和伺服器時間只差幾秒。
  - 拆成 `B`、`P`、`Z` 三筆記錄，照第 3 節比新舊。
- `GFTK` 沒有墓碑；0.8.x 的人關掉分享所在地時，只是不再帶 `Z`。這種情況交給保留期限處理。

## 3. 新舊比對（和 v1 相同，範圍擴大到所有群組）

| 收到的 vs 已存的（同一個 a、g） | 結果 |
|---|---|
| 沒有已存的 | 收（除非有更新的墓碑） |
| `t` 比較大、`h` 一樣 | 只把 `t` 往後推（確認） |
| `t` 比較大、`h` 不一樣 | 收新值 |
| `t` 比較小 | 不收；自己同步開啟的話，把自己較新的那份送出（同一筆 60 秒內只送一次，不管誰送的） |
| `t` 一樣、`h` 不一樣 | sender 是原作者本人的那份優先；都不是就取 `h` 比較大的 |
| 墓碑 `t` ≥ 記錄 `t` | 刪掉記錄 |

- `t` 比自己的 `GetServerTime()` 晚 10 分鐘以上的不收（防程式錯誤）；早於 2026-01-01 的也不收。
- **原作者自己的資料也照這張表比**。所以換電腦、存檔比較舊時，也能從公會拿回較新的。

## 4. 同步流程

### 4a. 上線（約 20 秒後，等名冊載入完；不在副本、戰鬥中）

1. 觀察自己的 `B`、`P`、`Z`（D-015 起沒有開關，取得到所在地就有 `Z`）並更新 `t`，然後送自己的 `I`（1 則）。
   - 收到的人比對：`t` 較新、`h` 相同的只推 `t`；`h` 不同的送 `G` 要；自己較新的送出去。
2. 送 `Q`。
3. 在線的人：自己的作者數和總摘要跟 `Q` 一樣就不回；不一樣就隨機等 2～8 秒，這段時間聽到別人回同一個 `qid` 的 `C` 就取消。**通常只有一個人回目錄**。
4. 新上線的人比對目錄：
   - 某位作者的 `d` 不一樣：放進要索引的清單，用 `A` 要（每秒 1 則）。
   - 自己手上有、目錄沒有的作者：送自己那份的 `I`，讓回目錄的人和其他人也能補。
5. 回 `A` 的人：原作者本人在線時由他回自己的 `I`（等 0～1 秒）；其他持有者隨機等 2～6 秒，聽到別人送了同一位的 `I`、而且摘要一樣，就取消。
6. 拿到 `I` 之後照第 3 節：要缺的或較新的（`G`），推 `t`，送出自己較新的。
7. 這次上線最多要 60 位作者的索引、120 筆資料，剩下的之後再補（下次有人上線時的 `Q`／`C` 也會順便補到）。0.10.0 起依名冊人數調高（`max(60, 名冊 × 0.6)`、`max(120, 名冊 × 2)`），在線的人和最近有變的先要，每 10 秒送一輪。

### 4b. 原作者有更新（線上期間）

- `B`、`P`：值改了就送 `V`（30 秒合併一次）。
- `Z`：換區域時送 `V`，5 分鐘最多一次。
- `R<id>`：配方清單改了，30 秒後送 `B`+`D`。
- 值沒改時不送；別人會從下次的 `I` 知道 `t` 更新了。

### 4c. 回答 `G`（轉傳）

- 手上那筆的 `t` 大於或等於要求的人都可以回。原作者本人優先（0～1 秒），其他人隨機等 2～6 秒，聽到別人送了就取消。
- `a`、`t`、`h` 原封不動。

### 4d. 關閉同步的人

- **原作者關閉同步**：送一則 `X~a~*`，然後不送任何 `I`、`V`、`B`、`D`，也不回 `A`、`G`、`Q`。
- **轉傳的人關閉同步**：不轉傳任何人的資料，也不回目錄（D-014 第 2 點，加上 D-011「關閉就完全不分享」）。
- **關閉同步的人可以收、可以看**（D-014 第 4 點）。他可以送 `Q`、`A`、`G` 來要資料。這三種請求不包含自己的任何資料，只是讓「可以看」真的看得到最新的。

## 5. 儲存

`GreenFangToolkitDB.share`，新的頂層欄位。GF Sync 不讀，要寫進合約（見草稿）。

```lua
share = {
  v = 1,
  guilds = {
    ["<realm>|<公會>"] = {
      rec = { ["<a>"] = { B = { t=…, h="…", v="60.WARRIOR", heardAt=…, via="<sender a>" },
                          P = {…}, Z = {…}, R164 = {…} } },
      tomb = { ["<a>"] = { ["*"] = t, Z = t, R164 = t } },
      queued = { ["<a>"] = { B = t, P = t, Z = t, R164 = t } }, -- 已寫進 outbox 的版本（第二段做，上傳用）
    },
  },
  seenIDs = { [recipeID] = true },  -- 已放進 recipe.names 的配方 ID（第二段做，上傳用）
}
```

- 自己的記錄也放在 `rec` 裡，用自己的 GUID。
- 現有的 `peers`（名冊畫面用）改由 `share` 產生：收到 `B`、`P`、`Z` 時更新 `peers[名字]`，名冊和提示框不用改。
- **保留期限**：
  - 原作者連續 14 天不在名冊上：刪除。名冊沒有載入完整時不刪。
  - 墓碑保留 60 天。
  - 一般記錄不會過期，畫面上標示「N 天前」。
- **大小**：115 人 × 約 1.5 KB（含配方）約 170 KB。上限 2,000 筆記錄；超過時先刪 `heardAt` 最舊、不在名冊上的人。0.10.0 起上限是 `max(2000, 名冊 × 10)`，滿了才刪（以前是新的不收）。
- 0.10.0 起 `share.guilds[*]` 多了 `queued`、`idsSent`、`named`（上傳用：這台電腦上次寫進 outbox 的版本），`share.seenIDs` 是放過 `recipe.names` 的配方 ID。GF Sync 不讀。

## 6. 頻率限制

- `GFTKS` 一條送出佇列：最多存 8 則，每秒回補 0.9 則。被節流（`SendAddonMessage` 回傳節流代碼）時額度歸 0。
- 副本或戰鬥中不送，佇列保留；超過 5 分鐘還沒送的資料訊息丟掉，之後再補。
- `AreOutgoingAddonChatMessagesRestricted()` 只在副本或戰鬥中參考，因為 GuildForge 實測在 Forever 上它幾乎一直是 true。
  - **現有的 `Comm.lua`（GFTK）在任何時候都參考它**，所以 0.8.x 的分享可能從來沒送出去過。第一段會一起照這個規則修正，並在報告裡標出來。
- 估計：20 人在線、1 人上線、他缺 10 位作者的索引和 20 筆資料。
  - 需要 `I` 1 則、`Q` 1 則、`C` 約 14 則、`A` 1 則、`I` 10 則、`G` 3 則，資料 `V` 約 20 則或配方 `B`+`D` 數十則。
  - 全公會約 50～100 則，分散在 1～2 分鐘內。

## 8. 介面（D-014 第 6 點）

- 遊戲內畫面只放玩家用得到的資訊：名冊、我的角色、配方、設定裡的兩個開關。
- 以下內容移到新的**「同步與診斷」**視窗：
  - 同步狀態
  - 待上傳筆數
  - 最新資料時間
  - GF Sync 說明
  - 分享統計（收到幾位、轉傳幾筆、佇列長度、被節流次數）
  - `/dump` 用的除錯資訊
- 開啟方式：設定頁右上角和名冊頁右上角各一個小按鈕「同步與診斷」；`/gftk sync status` 也會打開它。
- 名冊頁現在的同步狀態那一行，改成一個小圖示（綠＝開啟、灰＝關閉），滑鼠移上去顯示一句話。
- 這部分可以從 D9 開始做，和分享協定互不影響；排在第一段之後。
